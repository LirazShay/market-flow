# 1. Parity definition

Parity means:

~~~text
same validated provider scenario
→ same intended observable market facts
→ same Current Universe behavior
→ same Detail/History behavior
→ same failure/non-commit meaning
~~~

Parity does **not** require:

- the same persistence engine;
- the same private object model;
- the same table/index layout;
- the same helper functions;
- the same internal event order;
- preserving a legacy implementation bug.

---

# 2. Oracle authority hierarchy

When evidence disagrees, resolve it in this order.

## Tier 1 — current durable contracts

Highest authority:

- D-043;
- current product-shape contract;
- provider-data contract;
- recorder contract;
- Viewer contract;
- explicit durable acceptance behavior.

A newer explicit contract is not overridden merely because legacy code behaves differently.

## Tier 2 — verified V1 characterization

Use executable V1 characterization for preserved behavior not fully specified by durable docs.

Examples:

- sort tie behavior;
- history continuation behavior;
- missing optional metadata behavior;
- Current→Detail→Back state continuity.

## Tier 3 — existing public-contract tests

Tests are evidence, but may be stale.

A test that contradicts a newer durable decision is updated rather than treated as authority.

## Tier 4 — legacy implementation observation

Legacy code is evidence, not the oracle.

Implementation accidents are not automatically promoted to V2 requirements.

## Tier 5 — Unknown

If material behavior remains unresolved:

~~~text
Unknown
→ create narrowly scoped evidence/decision task
→ block only the affected parity claim
~~~

Unknown never becomes PASS.

---

# 3. Independent oracle strategy

Expected outcomes must not be generated by the same V2 implementation code being tested.

Preferred model:

~~~text
sanitized deterministic provider scenario
        ↓
frozen expected observable oracle
        ↓
V2 SQL-backed execution
        ↓
normalized observable result
        ↓
structural comparison
~~~

V1 is used while building/validating the oracle.

Once a scenario oracle is accepted, normal V2 CI does not need to execute the old IndexedDB implementation on every run.

This prevents:

- shared-helper false greens;
- permanent dual-runtime dependency;
- coupling to storage internals.

# 4. Scenario package contract

Each versioned parity scenario should contain conceptually:

~~~text
scenario metadata
provider inputs
fixed timestamps/clock
expected collector outcome
expected committed-market model
expected Current model
expected Detail/History model
expected failure/non-commit model
oracle provenance
~~~

Minimum metadata:

~~~text
scenarioId
scenarioVersion
description
contractAreas[]
fixtureVersion
oracleVersion
oracleStatus = Verified | Inferred | Unknown
sourceReferences[]
expectedResultKind
~~~

Fixtures are sanitized synthetic data only.

No authenticated raw response dump is committed.

# 5. Determinism rules

Use fixed values for:

- collection times;
- chunk receive times;
- provider/server times;
- SecurityIds;
- sort values;
- equal-timestamp cases;
- page boundaries.

Do not compare irrelevant implementation identities such as:

- DuckDB physical row IDs;
- OPFS file names;
- random UUIDs;
- transaction IDs;
- wall-clock test duration.

If identity semantics matter, compare invariants.

Example:

~~~text
runtime identity exists
and changes after runtime restart
~~~

rather than comparing one literal random value.

# 7. Value normalization rules

Normalization removes representation noise only.

## Preserve as distinct

~~~text
null
0
""
missing
false
numeric sign
SecurityId string identity
raw source distinctions
~~~

## Allowed normalization

- object key order;
- equivalent exact numeric wrappers;
- timestamp representation normalized to one canonical form when source meaning is unchanged.

## Forbidden normalization

Never collapse:

- null → 0;
- "" → null;
- missing → null;
- "0" → 0 without an explicit contract;
- stale → fresh;
- partial → complete;
- differing SecurityIds;
- differing product-defined row order.

# 8. Mandatory scenario corpus

## P-01 normal complete cycle

Multiple securities and chunks.

Proves baseline collector, Current and Detail/history.

## P-02 universe grows

A later cycle introduces a new SecurityId.

Expected:

- Current adds it;
- history begins only when real data exists;
- no hardcoded universe count.

## P-03 universe shrinks

A later cycle removes a SecurityId.

Expected:

- Current removes it;
- existing history remains;
- open Detail follows explicit not-current semantics.

## P-04 missing optional universe metadata

Expected:

- valid latest row remains visible;
- optional metadata stays missing;
- no fabricated value.

## P-05 null / zero / empty / missing

One scenario intentionally contains all four.

Expected:

- persisted facts remain distinct;
- UI zero remains zero;
- missing-display rules remain correct.

## P-06 equal timestamps

Two same-security snapshots share the same timestamp but have distinct stable snapshot/cycle identity.

Expected:

- deterministic total order;
- no duplicate/skip across continuation.

## P-07 repeated changed cycles

Expected:

- Current advances;
- history retains prior rows.

## P-08 security enters late

Expected:

- no fabricated historical rows before first appearance.

## P-09 security leaves and returns

Expected:

- Current membership follows latest complete universe;
- historical continuity remains.

## P-10 duplicate provider identity

Expected:

- validation failure;
- no commit;
- previous committed state preserved.

## P-11 missing requested identity

Expected:

- validation failure;
- no partial Current/history advancement.

## P-12 unexpected identity

Expected:

- validation failure;
- no partial success.

## P-13 malformed response

Expected:

- explicit failure;
- never interpreted as successful empty universe.

## P-14 provider failure mid-cycle

Expected:

- cycle fails;
- no state advancement;
- last good state remains observable with truthful health/error status.

## P-15 persistence failure before COMMIT

Expected:

- no attempted cycle state visible.

## P-16 lost acknowledgement after COMMIT

Expected:

- retry reconciles by ingest token;
- no duplicate cycle.

## P-17 Viewer opens after data already exists

Expected:

- authoritative state loads without needing a historical notification.

## P-18 missed notification

Expected:

- manual/reconnect reread restores correct state;
- notification payload is not authority.

## P-19 Viewer reload/reopen

Expected:

- product reconstructs from SQL authority/runtime state.

## P-20 Current→Detail→Back

Expected:

- canonical SecurityId;
- useful sort/viewport state preserved according to contract.

## P-21 live refresh while in Detail

Expected:

- Detail remains active;
- current/history refresh coherently;
- no forced return to Current.

## P-22 history read failure

Expected:

- localized Detail error;
- Current state remains healthy.

## P-23 runtime disconnect/re-attach

Expected:

- runtime unavailable state explicit;
- full resync on new runtime identity;
- no duplicate Recorder.

# 11. Collector parity assertions

Compare:

- universe discovery result;
- sequential chunk behavior;
- canonical IDs;
- requested/received/unique counts;
- duplicate/missing/unexpected sets;
- malformed/failing cycle classification;
- raw facts;
- source timing where contract-owned;
- successful-cycle handoff only after exact validation.

Do not require matching private fetch-helper call stacks.

# 12. Persistence parity boundary

V1 and V2 persistence are intentionally different.

Therefore parity compares effects:

~~~text
successful complete cycle
→ Current/history become one coherent newer state

failed cycle
→ no partial successful advancement
~~~

It does not compare:

~~~text
IndexedDB store count
DuckDB table count
index names
transaction primitives
physical keys
~~~

V2 has additional durability guarantees that may exceed V1; stronger guarantees are not parity failures.

# 14. Mismatch taxonomy

Every parity mismatch is classified before fixing code.

## IMPLEMENTATION_DEFECT

Current contract/oracle is correct; V2 behavior is wrong.

Action:

~~~text
add/retain regression
→ fix V2
→ rerun
~~~

## ORACLE_DEFECT

Expected fixture/oracle is wrong.

Action:

~~~text
prove against higher authority
→ update oracle version
→ document reason
→ rerun
~~~

## SPEC_DEFECT

Durable contracts are ambiguous/contradictory.

Action:

~~~text
resolve contract/decision first
→ update spec
→ update oracle
→ rerun
~~~

## LEGACY_BUG

V1 observed behavior conflicts with current intended contract.

Action:

~~~text
do not preserve bug as parity requirement
→ record characterization difference
→ assert intended V2 contract
~~~

## UNKNOWN

Evidence insufficient.

Action:

~~~text
no PASS
→ targeted evidence/decision task
~~~

# 15. Three-way disagreement procedure

When:

~~~text
V1 behavior != V2 behavior
and/or
spec != V1
~~~

use this procedure:

1. identify the exact contract area;
2. compare against Tier-1 durable authority;
3. inspect V1 characterization evidence;
4. inspect current public-contract tests;
5. classify as IMPLEMENTATION_DEFECT / ORACLE_DEFECT / SPEC_DEFECT / LEGACY_BUG / UNKNOWN;
6. change only the owning source;
7. bump oracle version if expected output changes;
8. retain a regression protecting the resolved public behavior;
9. rerun the scenario and affected suite.

Do not “make both sides match” without first deciding which behavior is correct.

---

# 16. Oracle change control

Oracle files are production-test assets.

Changing expected output requires:

- explicit scenario ID;
- reason;
- authority/source supporting the change;
- oracle version bump;
- affected contract areas;
- review by the same CI guards that protect implementation changes.

A product implementation change and oracle expectation change in the same commit are allowed only when the reason is explicit and the changed contract is independently justified.

Otherwise, changing both together is suspicious because it can hide regressions.

# 17. Test-layer mapping

## Node

Best for:

- collector validation policy;
- canonical ID rules;
- normalization;
- oracle parsing;
- diff generation;
- sort/paging pure logic;
- mismatch classification.

## Chromium

Required for:

- DuckDB/OPFS;
- transaction/reopen behavior;
- trusted runtime reads;
- Viewer rendering/navigation;
- equal-timestamp paging integration;
- reload/recovery;
- failure injection involving browser/runtime components.

## Live authenticated Leumi

Only for facts CI cannot prove:

- actual origin compatibility;
- real provider flow;
- live source-field presence/shape;
- production-shaped L-2 compatibility.

Live evidence validates provider/runtime premises; it does not replace deterministic parity scenarios.

Normal feature work:

~~~text

→ targeted Chromium parity scenarios
~~~

Before ND-16:

~~~text
all parity scenarios
+ full Browser CI
~~~

---

# 19. Pass/fail rules for ND-16

ND-16 may be PASS only when:

- every mandatory parity scenario is PASS or explicitly NOT_APPLICABLE for a contract area;
- no mandatory scenario is Unknown;
- no unexplained mismatch remains;
- full Browser CI is green;
- Fast CI is green;
- L-2 is PASS;
- evidence is tied to the exact candidate commit/build;
- sanitization/security guard is green.

If one scenario is unresolved, ND-16 remains verification-pending.

---

# 20. Freshness rules

Parity evidence becomes stale when a dependent area changes.

Examples:

- collector change invalidates collector + downstream parity;
- SQL persistence/read-contract change invalidates committed-state/Current/Detail parity;
- Viewer sorting change invalidates Current UI parity;
- history cursor change invalidates Detail/history parity;
- fixture/oracle change invalidates every scenario using that fixture/oracle.

The final guards should map source areas to parity suites so stale evidence is visible.

---

# 21. Shadow fallback boundary

Shadow comparison is **not** the default parity mechanism.

It is activated only if:

- deterministic corpus is green;
- L-2 is working;
- a material migration uncertainty remains that cannot be resolved otherwise.

If used:

~~~text
temporary shadow evidence
→ resolve uncertainty
→ retire shadow machinery
→ rerun ND-16
~~~

Shadow never becomes a permanent second market-data authority.

Pass E2 planning is complete when the implementation plan has an unambiguous answer to:

- what parity means;
- what the oracle is;
- how expected results are created;
- what scenarios are mandatory;
- what is compared;
- what is deliberately not compared;
