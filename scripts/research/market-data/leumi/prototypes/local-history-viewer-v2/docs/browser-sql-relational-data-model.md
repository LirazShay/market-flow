# Browser SQL — Relational Data Model

This is the Phase F relational-model artifact for Local History Viewer V2.

It defines the selected schema direction for the Browser SQL target. It does not define the ingest algorithm, transaction ordering, scheduler policy, retention policy or migration implementation.

Live progress remains owned only by ../STATUS.json.

Durable decision:

~~~text
../../../../../../../docs/project/decisions/D-027.md
~~~

## 1. Core model

Target market-history tables:

~~~text
schema_meta
recording_session
security
current_universe
cycle
snapshot
latest_snapshot
~~~

Later phases may add query-definition/execution and operational tables.

## 2. Identity model

Canonical security identity remains:

~~~text
security_id = String(PaperId or Key)
SQL type    = VARCHAR
~~~

Stable SQL identities:

~~~text
session_id  BIGINT
cycle_id    BIGINT
snapshot_id BIGINT
~~~

Rules:

- IDs are generated by the SQL authority.
- SnapshotId is not derived from timestamp.
- Time is never the primary identity.
- snapshot has UNIQUE(cycle_id, security_id).
- one successful cycle contains at most one snapshot per security.

## 3. schema_meta

Purpose: own Market Flow logical schema version independently from the DuckDB file/package version.

Logical columns:

~~~text
schema_version       INTEGER
schema_name          VARCHAR
created_at_ms        BIGINT
last_migrated_at_ms  BIGINT NULL
~~~

Destructive database reset is not a migration strategy.

## 4. recording_session

Logical columns:

~~~text
session_id             BIGINT PRIMARY KEY
started_at_ms           BIGINT NOT NULL
stopped_at_ms           BIGINT NULL
status                  VARCHAR NOT NULL
config_json             JSON NULL
initial_universe_count  BIGINT NULL
completed_cycles        BIGINT NOT NULL
failed_cycles           BIGINT NOT NULL
stop_reason             VARCHAR NULL
~~~

A new Recorder run creates a new session without deleting prior history.

## 5. security

Purpose: latest known MapHeat/universe metadata for every security ever seen.

Logical columns:

~~~text
security_id          VARCHAR PRIMARY KEY
paper_name           VARCHAR NULL
map_heat_updated_ms  BIGINT NULL
raw_map_heat         JSON NOT NULL
~~~

Rules:

- full raw MapHeat record is retained;
- a security may remain in this catalog after leaving the current universe;
- this table is metadata/catalog, not historical market state.

## 6. current_universe

Purpose: exact currently validated universe membership.

Logical columns:

~~~text
security_id   VARCHAR PRIMARY KEY
loaded_at_ms  BIGINT NOT NULL
~~~

This is intentionally separate from security.

Benefits:

- current membership can be replaced as one coherent set;
- old securities remain discoverable in security;
- no hardcoded universe size;
- membership is explicit rather than inferred.

## 7. cycle

Purpose: one collection attempt and its integrity/diagnostic outcome.

Logical columns:

~~~text
cycle_id          BIGINT PRIMARY KEY
session_id        BIGINT NOT NULL
status            VARCHAR NOT NULL
started_at_ms     BIGINT NOT NULL
completed_at_ms   BIGINT NULL
duration_ms       BIGINT NULL
requested_count   BIGINT NULL
received_count    BIGINT NULL
unique_count      BIGINT NULL
duplicate_count   BIGINT NULL
missing_count     BIGINT NULL
unexpected_count  BIGINT NULL
chunk_diagnostics_json JSON NULL
error_json             JSON NULL
~~~

Initial status domain:

~~~text
complete
failed
~~~

Rules:

- successful snapshots exist only for a complete cycle;
- failed cycles own no successful snapshot rows;
- unknown diagnostics remain NULL rather than guessed.

## 8. snapshot — authoritative historical fact

One row represents one security in one successful cycle.

Primary identity:

~~~text
snapshot_id BIGINT PRIMARY KEY
~~~

Natural uniqueness:

~~~text
UNIQUE(cycle_id, security_id)
~~~

Core metadata:

~~~text
snapshot_id           BIGINT
cycle_id              BIGINT
session_id            BIGINT
security_id           VARCHAR
chunk_index           INTEGER NULL
cycle_started_at_ms   BIGINT
chunk_received_at_ms  BIGINT NULL
collected_at_ms       BIGINT
server_as_of_raw      VARCHAR NULL
~~~

Full provider record:

~~~text
raw_security JSON NOT NULL
~~~

The complete GetSecuritiesData Security object is retained.

Provider-owned time fields remain raw unless their semantics are separately Verified.

## 9. Raw + typed analytical strategy

Selected rule:

~~~text
raw JSON
= complete source preservation and future unknown-field access

typed promoted columns
= fast common SQL predicates/calculations
~~~

Initial promoted fields should include logical equivalents of the repeatedly used values:

~~~text
last_rate
daily_deals_quantity
bid1
ask1
mid
~~~

Representative types:

~~~text
price/rate-like values       DOUBLE NULL
cumulative count-like values BIGINT NULL
mid                          DOUBLE NULL
~~~

A field is promoted only when its source mapping and semantics are sufficiently Verified.

The raw value remains available even after promotion.

## 10. Null / zero / empty / missing

Promoted SQL NULL cannot by itself prove whether a source JSON key was absent or explicitly null.

Therefore raw JSON remains the source-presence evidence.

Required semantics:

~~~text
missing != null != 0 != ""
~~~

- zero remains numeric zero;
- empty string remains empty string;
- explicit JSON null remains explicit null;
- absent property remains absent;
- promoted NULL means only that no typed value is available.

When source presence matters, SQL must inspect raw JSON semantics.

No presence-flag column is added for every provider field by default.

## 11. Time model

Canonical Market Flow-generated timestamps remain:

~~~text
BIGINT epoch milliseconds
~~~

Examples:

~~~text
started_at_ms
completed_at_ms
collected_at_ms
chunk_received_at_ms
~~~

This preserves inherited semantics, avoids local-time ambiguity and exchanges cleanly with JavaScript.

Human-readable timestamp expressions/views may be added for SQL ergonomics.

## 12. latest_snapshot

Purpose: fast current access without duplicating the full snapshot.

Logical columns:

~~~text
security_id  VARCHAR PRIMARY KEY
snapshot_id  BIGINT NOT NULL UNIQUE
~~~

Relationship:

~~~text
latest_snapshot.snapshot_id
→ snapshot.snapshot_id
~~~

Selected rule:

latest_snapshot is a pointer table, not a duplicate full market row.

A convenience view may later expose current_snapshot by joining latest_snapshot to snapshot and security/current_universe.

Benefits:

- no duplicate raw JSON;
- latest replacement is small;
- current queries avoid history scans;
- the authoritative detailed fact exists once.

Exact update/removal semantics belong to Phase G.

## 13. Core horizons

Current core horizons:

~~~text
10s
20s
30s
60s
90s
120s
300s
600s
~~~

Selected physical direction:

Use wide nullable snapshot columns for this small core set.

For each horizon H:

~~~text
prev_H_snapshot_id
last_change_H_pct
deals_delta_H
~~~

Example:

~~~text
prev_120s_snapshot_id
last_change_120s_pct
deals_delta_120s
~~~

Why wide columns:

- no eight-row child expansion for every snapshot;
- simpler user SQL;
- fewer common joins/pivots;
- strong fit for a small heavily reused set;
- favors the live workload over theoretical generic flexibility.

The horizon list must have one canonical definition in code/config.

Changing core horizons later is explicit schema evolution.

## 14. Temporal-link semantics

Each prev_H_snapshot_id is nullable.

Required logical invariant:

~~~text
current.security_id = previous.security_id
previous.collected_at_ms < current.collected_at_ms
~~~

The referenced row is the actual collected snapshot selected near the intended horizon.

Exact nearest-snapshot/tolerance logic belongs to Phase G.

If history is not available:

~~~text
prev_H_snapshot_id = NULL
last_change_H_pct  = NULL
deals_delta_H      = NULL
~~~

History is never fabricated.

## 15. LAST change

When the verified current and previous LAST/rate values exist:

~~~text
last_change_H_pct =
((current_last - previous_last) / previous_last) * 100
~~~

Stored as:

~~~text
DOUBLE percentage points
~~~

Example:

~~~text
0.5 = +0.5%
~~~

If either value is unavailable or the previous denominator is zero, the metric is NULL.

## 16. Deals delta

Core horizon columns exist logically:

~~~text
deals_delta_10s
...
deals_delta_600s
~~~

But they must remain unpopulated/NULL until cumulative deal-count semantics are Verified.

No subtraction is authorized merely because a provider field name looks plausible.

## 17. MID

Logical target:

~~~text
mid = (bid1 + ask1) / 2
~~~

only when both source mappings are Verified and both typed values are available.

Numeric zero is not automatically treated as missing.

If one side is unavailable, mid is NULL.

## 18. Relationships

~~~text
recording_session
  1 ─── * cycle

cycle
  1 ─── * snapshot

security
  1 ─── * snapshot

current_universe
  * ─── 1 security

latest_snapshot
  * ─── 1 snapshot

snapshot
  ─── optional self-reference per core horizon
~~~

These are logical relationships.

Whether every relation uses a physical DuckDB FOREIGN KEY constraint is deferred; correctness and transaction behavior matter more than adding constraints reflexively.

## 19. Query capability

Current rows:

~~~sql
SELECT s.*
FROM latest_snapshot l
JOIN snapshot s
  ON s.snapshot_id = l.snapshot_id;
~~~

Two-minute historical link:

~~~sql
SELECT cur.security_id,
       cur.last_rate,
       old.last_rate
FROM snapshot cur
JOIN snapshot old
  ON old.snapshot_id = cur.prev_120s_snapshot_id;
~~~

Cross-security ranking:

~~~sql
SELECT s.security_id,
       s.last_change_30s_pct
FROM latest_snapshot l
JOIN snapshot s
  ON s.snapshot_id = l.snapshot_id
ORDER BY s.last_change_30s_pct DESC
LIMIT ?;
~~~

These are schema examples, not trading rules.

## 20. Rejected generic EAV metric design

Core metrics will not use a generic structure such as:

~~~text
snapshot_metric(
  snapshot_id,
  metric_name,
  horizon,
  value
)
~~~

for the current core set.

Reasons:

- more rows;
- weaker typing;
- more verbose live SQL;
- repeated name/value interpretation;
- flexibility is already provided by raw JSON, linked snapshots and arbitrary SQL.

A future related structure requires a concrete new need.

## 21. Rejected full latest-row duplication

The target will not store:

~~~text
full snapshot in history
+
full duplicate snapshot in latest
~~~

The pointer table keeps one authoritative fact.

## 22. Schema version ownership

Market Flow owns one explicit logical schema version.

Schema evolution includes changes to:

- core tables;
- column semantics;
- core horizon columns;
- uniqueness/identity;
- raw representation.

Schema upgrades must migrate deliberately and must not silently erase persistent history.

Exact migration behavior belongs to Phase I.

## 23. Deferred

Phase F does not decide:

- Arrow batch layout;
- exact bulk-ingest API;
- BIGINT sequence syntax;
- transaction statement order;
- temporal-link lookup algorithm/tolerance;
- writer/query priority;
- CHECKPOINT cadence;
- retention;
- query-definition/execution tables;
- result transport;
- exact DuckDB package version;
- existing IndexedDB import.

## 24. Completion result

Selected model:

~~~text
schema_meta
recording_session
security + current_universe
cycle
snapshot
  + full raw_security JSON
  + small promoted typed set
  + wide core-horizon links/metrics
latest_snapshot pointer table
~~~

Key invariants:

~~~text
SecurityId = VARCHAR canonical identity
SnapshotId = stable BIGINT surrogate
UNIQUE(cycle_id, security_id)
raw provider record is preserved
latest is a pointer, not a duplicate fact
core horizons are wide nullable columns
missing history remains NULL
source missing/null/zero/empty remains recoverable from raw JSON
~~~

This model is the input to Phase G ingest/enrichment/atomicity planning.
