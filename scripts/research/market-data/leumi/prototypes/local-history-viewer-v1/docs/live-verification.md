# Live Leumi Verification Procedure

This document defines the safe, reproducible procedure for provider-dependent validation of the assembled Local History Viewer V1 runtime.

Operational progress belongs only in `../STATUS.json`.

Normative Debug Bundle behavior is owned by:

~~~text
../specs/debug-bundle.spec.md
~~~

## Safety boundary

Run the generated Bookmarklet only inside the user's already-authenticated Leumi browser tab.

Do not copy, commit, upload or paste:

- cookies;
- authorization headers;
- session tokens;
- account numbers;
- private browser/session storage;
- authenticated HAR files;
- screenshots that expose account/private financial data.

The verification report should contain only sanitized behavior/results and non-sensitive counters.

The normal diagnostic artifact is the bounded sanitized Debug Bundle generated by the running Market Flow runtime. Do not replace it with ad-hoc browser-storage or raw-provider dumps.

## Prerequisite

Use a runtime artifact generated from the repository sources:

~~~text
npm run build:runtime
~~~

Generated Bookmarklet:

~~~text
runtime/dist/market-flow-v1.bookmarklet.txt
~~~

The rolling release or a Browser CI artifact may also be used when it was produced from the exact verified code state being tested.

Optional manual helper:

~~~text
../debug/live-verification-check.js
~~~

Run that helper only after the verified Market Flow runtime is already running. It is observational: it uses the existing Debug Bundle API, does not start another recorder, does not make provider requests, and downloads a sanitized live-verification JSON report.

## Verification sequence

### 1. Launch on the real Leumi origin

Open the intended Leumi market page while already authenticated, then execute the generated Bookmarklet.

Expected observable behavior:

- `window.MarketFlowRuntime` exists;
- the recorder starts;
- the same-origin viewer opens;
- the viewer does not require copied market rows from the opener;
- no external code host is contacted by the Bookmarklet.

### 2. Allow several recorder attempts

Let the recorder run for several cycles/attempts so the live behavior is represented in persisted diagnostics.

Do not require a successful cycle before collecting evidence.

For a healthy run, expected recorder behavior is:

- `completedCycles >= 1`;
- `failedCycles === 0`;
- successful cycles report requested/received/unique equality;
- the universe count is dynamic rather than assumed.

For a failing run, especially `completedCycles === 0`, continue directly to the Debug Bundle export. The failure itself is the evidence to diagnose; do not repeatedly reload or alter the runtime before capturing it.

### 3. Export the sanitized Debug Bundle

In the Viewer, click:

~~~text
הורד קובץ Debug
~~~

Equivalent runtime API:

~~~js
await MarketFlowRuntime.downloadDebugBundle()
~~~

For a one-step manual verification report, run:

~~~text
../debug/live-verification-check.js
~~~

It downloads a file named like:

~~~text
market-flow-live-verification-YYYYMMDDTHHMMSSZ.json
~~~

The helper includes PASS/NEEDS_REVIEW checks plus the same bounded sanitized Debug Bundle evidence. A PASS means the automated live checks in that helper passed; it does not by itself prove manual UI interactions such as sorting, history drill-down, repeated launch or stop/restart.

The normal Debug Bundle file is named like:

~~~text
market-flow-debug-YYYYMMDD-HHMMSS.json
~~~

Inspect the bounded fields that already belong to the diagnostic contract:

- `runtime.recorder.status`, `completedCycles`, `failedCycles` and `latestError`;
- `runtime.persistence`;
- `runtime.viewer`;
- `database.rowCounts`;
- `recentCycles` status/counters/errors;
- market-data and provider-time fingerprints for complete cycles;
- changed-security counts between adjacent complete cycles;
- `latestCompleteCycle` when available;
- the `safety` flags confirming that raw payload/session data was not intentionally collected.

Important interpretation rule:

~~~text
no complete cycle
!=
no useful Debug Bundle
~~~

When there are only failed cycles, fingerprint fields are expected to be unavailable for those failed cycles. Use the persisted failure summaries and `runtime.recorder.latestError` first; do not invent market/provider freshness conclusions that the bundle cannot prove.

### 4. Confirm real provider behavior only as far as the evidence supports

The Debug Bundle proves what reached the Market Flow runtime/persistence boundary. It does not replace endpoint-specific browser evidence when the failure happens before a complete cycle is built.

If endpoint-level confirmation is needed, DevTools Network may be used only to record sanitized observations:

- endpoint name: `MapHeat2` or `GetSecuritiesData`;
- HTTP status;
- request count;
- non-sensitive response-shape observation.

Do not export or share authenticated request headers, cookies, tokens, full response payloads or HAR files.

Classify any provider claim that is not directly observed as `Inferred` or `Unknown`, not `Verified`.

### 5. Viewer verification

When at least one complete cycle exists, confirm from the Viewer UI:

- current rows render from IndexedDB;
- the row count is consistent with the persisted latest snapshot;
- sorting works;
- opening one security shows persisted history;
- viewer refresh follows a committed cycle;
- manual refresh remains DB-only.

If no complete cycle exists, record Viewer current/history verification as blocked by the recorder failure rather than treating an empty viewer as a separate viewer defect.

### 6. Repeated launch

Execute the same Bookmarklet again while the recorder is running.

Expected:

- no second recorder instance;
- an existing viewer may be focused/reused or another same-origin viewer may open;
- every viewer remains a read-only IndexedDB-backed view rather than creating another recorder.

### 7. Stop/restart

Stop through:

~~~js
await MarketFlowRuntime.stop(
    "live-verification"
);
~~~

Wait for completion, then execute the Bookmarklet again.

Expected:

- the prior stop persistence completes;
- a new recorder instance starts cleanly;
- existing IndexedDB history remains available;
- the viewer can reread persisted state.

If the recorder is failing before any successful cycle, stop/restart still verifies lifecycle/recovery behavior but does not convert provider-dependent checks into `Verified`.

## Result classification

Record every material outcome as one of:

~~~text
Verified
Inferred
Unknown
~~~

Use `Verified` only for behavior directly observed in the real authenticated Leumi browser session.

Use `Inferred` for conclusions supported by CI/mock behavior plus live observations but not directly proven.

Use `Unknown` when the live session does not expose enough evidence.

## Minimum acceptance evidence

A live verification result should contain, without secrets/private data:

- exact repository commit/runtime artifact used;
- browser/date;
- Bookmarklet launch result;
- Debug Bundle filename and sanitized findings;
- sanitized MapHeat2/GetSecuritiesData observations when endpoint-level evidence was needed;
- recorder/persistence result;
- viewer behavior result or explicit blocker;
- repeated-launch result;
- stop/restart result;
- any failures/errors with private data removed;
- `Verified` / `Inferred` / `Unknown` classification for each material item.

Do not proceed to long-run live validation until the required live checks have actually been executed and recorded.
