# D-040 — Browser SQL uses one stable exclusive Web Lock for cross-tab runtime authority

Status: Superseded by D-045 for Local History Viewer V2

## Current clarification

A browser Web Lock is no longer the database-ownership authority.

Under D-045, one localhost Node.js service owns the native DuckDB database. Browser tabs are transport/producer clients and never own the database file.

The exact single-instance Node process policy and active-browser-producer policy remain replacement-plan details; the historical Web-Lock topology below is retained for evidence.

## Decision

Market Flow V2 uses the browser Web Locks API as the sole cross-tab ownership authority for its Recorder/storage runtime.

Stable lock name:

~~~text
market-flow:local-history-viewer-v2:runtime-owner
~~~

The lock name is stable across builds, DuckDB versions and database epochs.

## Startup

A page-local singleton check occurs first.

An independent tab must acquire the exclusive runtime-owner lock with fail-fast semantics before creating the SQL Worker, opening production storage, or starting provider collection.

If the lock is unavailable, the tab remains passive.

## Failure/takeover

Correctness does not depend on heartbeat expiry.

Browser termination/unload releases the Web Lock; a later explicit launch may acquire it and must run durable readiness/recovery before Recorder start.

`steal:true` is forbidden because the previous holder's code may continue executing and cause split-brain.

## Messaging

BroadcastChannel and `navigator.locks.query()` are diagnostic/transport surfaces only and cannot grant authority.

## Verification boundary

C10 proves the ownership mechanism deterministically in Chromium before daily-readiness convergence.

C12 proves the same canonical lock behavior with two authenticated same-origin Leumi tabs before production cutover.

Real-origin ownership proof is therefore a final-cutover requirement, not an early blocker for C02-C09 implementation.
