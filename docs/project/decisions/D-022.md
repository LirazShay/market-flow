# D-022 — Failure-to-learning loop and continuous improvement

Status: Accepted

Decision:

Meaningful unexpected failures are not complete at "fixed and green".

Market Flow requires a lightweight learning review:

~~~text
unexpected failure
→ technical root cause
→ reasoning/process cause
→ escape cause
→ smallest prevention
→ generalization check
→ promote only reusable lessons
→ verify
~~~

The review must explicitly ask:

1. What technically failed?
2. What assumption/choice/process led us to create the condition?
3. Why did existing tests/review/specs/verification not catch it earlier?
4. What would we do differently if starting again?
5. What is the cheapest effective prevention?

Lessons are promoted only when they pass the repository's Promotion Gate: generalizable, actionable, preventive, evidence-based, cost-effective, KISS-compatible, and non-duplicative.

Expected TDD red is not itself an incident.

Durable lessons go to the narrowest correct owner (test, code invariant, SPEC, testing guide, engineering practice, AGENTS rule or durable decision). Current incident/run state remains in STATUS.json.

Why:

- fixing symptoms without learning allows the same failure class to recur;
- many expensive engineering mistakes begin as wrong assumptions rather than coding errors;
- understanding the escape cause improves both quality and development speed;
- distilling only reusable lessons avoids instruction bloat and process theater;
- the repository should become easier and safer to change after every meaningful failure.
