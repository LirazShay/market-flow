# D-020 — Tests-first pyramid with mandatory Chromium verification after code changes

Status: Accepted / evolved

Decision:

~~~text
new deterministic behavior
→ define meaningful tests first where practical
→ fast Node unit tests / Fast CI

browser TDD red phase
→ exact targeted Playwright test in Chromium
→ prove intended red without paying full-suite cost

after production/runtime/browser code changes
→ Chromium verification on final changed state
→ targeted for truly localized change
→ full Browser suite for shared runtime/harness/storage/messaging/viewer integration,
   cross-component or multi-area changes

every numbered Stage closure
→ full Browser CI

real provider behavior
→ live verification only when required
~~~

For bug fixes:

~~~text
regression test
→ targeted red
→ root-cause analysis
→ fix
→ targeted green
→ required Chromium breadth
→ Failure Review / learning disposition
→ keep the regression test
~~~

For Local History Viewer V1:

- Fast CI remains the cheap feedback loop.
- Expected browser TDD red should use the exact targeted test rather than a full Browser suite.
- Every production/runtime/browser code change must receive Chromium verification on its final state.
- Small localized changes may use a targeted Chromium test/spec for the immediate verification gate.
- Shared runtime/harness/storage/messaging/viewer-integration, cross-component or multi-area changes require the full Browser suite.
- Every numbered Stage closure requires fresh full Browser CI.
- IndexedDB is exercised in real Chromium when transaction/storage semantics matter.
- DOM/BroadcastChannel should use browser implementations where practical.
- MapHeat2 and GetSecuritiesData are mocked in CI with deterministic sanitized fixtures.
- live Leumi checks remain separate and must not put credentials/session state in GitHub Actions.
- tests protect observable/public contracts, not incidental private implementation details.
- meaningful unexpected failures also follow D-022 / the continuous-improvement Failure Review.

Authoritative workstream testing policy:

~~~text
scripts/research/market-data/leumi/prototypes/local-history-viewer-v1/tests/TESTING_POLICY.md
~~~

Why:

- targeted red/green keeps the TDD micro-loop fast;
- final changed code still receives real browser proof;
- broad integration changes receive broad browser regression;
- Stage closure keeps a strong full-suite safety net;
- CI remains reproducible and independent from private sessions;
- failures become learning inputs rather than only patches.
