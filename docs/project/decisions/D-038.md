# D-038 — Browser SQL storage lifecycle uses retain-all plus explicit archive-and-rollover

Status: Accepted

## Decision

The initial Browser SQL production target does not automatically prune history.

Default:

~~~text
retain-all
~~~

When storage pressure becomes material, the runtime warns using a benchmark-derived byte reserve and offers an explicit maintenance path.

The destructive space-recovery path is a whole-database history-epoch rollover rather than relying on row DELETE/VACUUM to reclaim quota.

## Rationale

DuckDB documents that checkpointing may reclaim deleted-row space only partially and VACUUM does not reclaim deleted-row disk space.

Therefore arbitrary session/age DELETE is not accepted as a guaranteed quota-management strategy.

## Archive semantics

Before rollover the user may create a logical local archive export.

That export is not described as a verified restorable backup until a future restore/import contract exists.

Proceeding without archive requires explicit irreversible confirmation.

## Epoch semantics

Each production DB has a database_epoch_id.

Rollover creates a fresh epoch, preserves designated active query/runtime configuration, but does not carry old market history or old query execution history into the new live database.

Live SQL never silently spans multiple epochs.

## OPFS safety

Market Flow may delete only its exact owned OPFS entries.

It must never clear the Leumi origin's complete OPFS.

## Recovery

Rollover uses a small non-secret maintenance journal and keeps Recorder stopped until startup can prove exactly one coherent production database epoch.
