# D-045 — Local History Viewer V2 uses a loopback Node.js SQL authority

Status: Accepted

## Evidence trigger

The Browser-SQL process boundary was reopened by direct C01 evidence.

On the real authenticated Leumi origin, the exact pinned candidate reached:

~~~text
bookmarklet bootstrap     = Verified
Blob Worker creation      = Verified
Worker asset load         = Verified
Wasm instantiate          = failed / Unknown
probe cleanup             = Verified
~~~

The failed stage was `wasm-instantiate`.

Separately, a minimal real-origin smoke test proved:

~~~text
https://hb2.bankleumi.co.il
→ ws://127.0.0.1:8765
→ local Node.js WebSocket server
→ test message received
~~~

This is sufficient evidence to stop coding forward on the known-bad Browser-SQL runtime premise and reopen the process boundary.

## Decision

The current V2 target architecture is:

~~~text
authenticated Leumi page
→ preserved provider acquisition + complete-cycle validation
→ loopback WebSocket
→ one local Node.js service
→ native DuckDB database
→ trusted local reads / SQL
→ Current + Detail/History + Dynamic SQL Scanner
~~~

No remote application server is introduced.

## Authority model

### Authenticated Leumi page

Owns provider authentication, provider calls, and creation of one validated complete-cycle market-data message.

It does not own durable V2 market history, SQL execution, the DuckDB file, or final database commit authority.

### Loopback WebSocket

Owns transport only. It is not durable storage, market-history authority, an authentication tunnel, or a source of truth.

### Local Node.js service

Is the sole target V2 SQL/history authority after cutover.

It owns database lifecycle, transaction/commit boundary, persisted raw/current/history data, trusted read APIs, Scanner execution, and service health/readiness.

The service binds to loopback only unless a later explicit decision changes that boundary.

### Native DuckDB

The database is owned only by the local Node.js service.

Browser tabs and Viewer clients do not open independent database handles.

The exact maintained Node package/version and DB file contract are selected and pinned later in the re-plan. D-045 fixes the process boundary, not an npm package version.

### Viewer / Scanner clients

Consume trusted local service APIs. They are clients, not independent persistence authorities.

## Security boundary

Provider cookies, session tokens, authorization headers, account identifiers and private browser/session state stay in the authenticated browser context and are not copied to the Node service.

Only market data and minimal non-sensitive protocol metadata required by V2 cross the loopback bridge.

The public repository continues to use sanitized synthetic fixtures only.

## KISS consequences

The current production plan no longer requires DuckDB-Wasm, OPFS database ownership, Wasm loading inside the bank page, Blob SQL Worker lifecycle, browser DB Web Locks, cross-tab OPFS coordination, or browser Wasm memory as the SQL-engine ceiling.

Historical Browser-SQL assets remain evidence/reference until the replacement plan classifies each as keep/adapt/archive/retire.
