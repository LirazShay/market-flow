# D-033 — Browser SQL verification uses Node + Chromium + mandatory live Leumi gates

Status: Accepted

## Decision

Local History Viewer V2 Browser SQL verification will use three distinct layers:

~~~text
Node unit tests
→ deterministic policy/state/data logic

Playwright Chromium
→ real Worker/Wasm/OPFS/runtime/Viewer/browser semantics

authenticated Leumi live verification
→ actual page CSP/origin/provider compatibility that CI cannot prove
~~~

Each public contract must be assigned to the cheapest layer that can actually prove it.

## Tests protect public behavior

Tests target observable contracts and authority boundaries rather than private implementation details.

Private queue shape, helper names, exact internal SQL statement ordering and other implementation details are not test contracts unless they become externally meaningful.

## Live compatibility gate

Before heavy Browser SQL implementation depends on the page-runtime architecture, a minimal real authenticated-Leumi probe must prove:

~~~text
injected JavaScript / Bookmarklet executes
→ Blob Worker works
→ exact pinned DuckDB Worker loads
→ exact pinned Wasm instantiates
→ intended OPFS database can open
→ synthetic write + COMMIT + CHECKPOINT
→ refresh/relaunch
→ reopen
→ synthetic data survives
~~~

This gate uses synthetic data only and must not capture or persist provider credentials/session material.

If the gate fails because of actual CSP/origin/browser policy, dependent implementation work pauses and the delivery architecture is revisited explicitly.

Mocks and ordinary Chromium CI cannot substitute for this live proof.

## CI split

Fast CI remains the normal push/PR gate and runs deterministic Node tests.

Browser CI remains separate and is required for browser-dependent implementation changes, changed browser tests/harness, numbered Stage closure and runtime publication.

Targeted Chromium runs are preferred during TDD/debugging; full Browser CI is the closure/release gate.

## Fixtures

All fixtures are sanitized and synthetic.

Browser SQL fixtures must cover complete/partial cycles, null/zero/empty/missing source values, temporal jitter/warm-up, query errors/zero rows, transaction/recovery ambiguity, CSP/capability failures and multi-Viewer behavior.

## Performance boundary

Ordinary correctness CI uses small deterministic datasets.

Trading-session and multi-million-row workloads belong to the dedicated benchmark strategy, not normal regression tests.

## Relationship

- D-031: runtime delivery requires real-page capability evidence.
- D-032: Viewer/result contracts require browser integration verification.
- D-033: assigns Browser SQL contracts to Node, Chromium and live verification layers.
