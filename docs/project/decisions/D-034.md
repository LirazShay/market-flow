# D-034 — Browser SQL performance is gated by cadence-relative headroom and full-session evidence

Status: Accepted

## Decision

Browser SQL performance decisions will be based on deterministic Chromium benchmarks using the real DuckDB-Wasm/OPFS runtime and parameterized synthetic market data.

Universe size and cadence are benchmark parameters, not correctness constants.

## Primary normal-profile gates

Correctness is mandatory before timing is interpreted.

For representative normal workload:

~~~text
p95 isolated durable ingest <= 25% of collection cadence
p95 isolated query service <= 25% of query cadence
p95 mixed ingest wait+service <= 50% of collection cadence
p95 mixed query lateness+service <= 50% of query cadence
normal-profile coalesced query ticks = 0
query overlap = 0
~~~

These ratios encode substantial headroom rather than accepting a system that merely finishes just before the next tick.

Changing the ratios later requires benchmark evidence and a durable/documented rationale.

## Capacity gates

Before Browser SQL cutover:

- representative full-session workload must complete correctly on target Windows/Chrome hardware;
- a 2x-session stress/capacity run (or explicitly justified equivalent) must complete without OOM, corruption or quota failure;
- no sustained backlog or unexplained monotonic memory-growth trend is acceptable;
- storage growth and reopen time must be measured as data volume grows.

## Workload scope

Benchmark covers:

- durable ingest including enrichment + CHECKPOINT;
- representative SQL filter/ranking/group/window/history/raw-JSON workloads;
- mixed ingest + scheduled SQL;
- result streaming/preview;
- memory;
- OPFS growth/quota;
- reopen/recovery;
- hidden/background behavior as a separate measured dimension.

## Environment

Primary decision environment is representative Windows + Chrome/Chromium.

GitHub/Linux Chromium timings are regression/trend evidence, not production timing proof.

Every result records exact repository commit, DuckDB-Wasm artifact/core version, browser/OS/hardware and dataset/query parameters.

## Heavy benchmark cadence

Multi-million-row/full-session/soak benchmarks do not run on every commit.

They are checkpoint/pre-cutover evidence. Normal CI remains correctness-focused.

- D-029 defines scheduler cadence/no-overlap behavior.
- D-030 makes CHECKPOINT part of durable cycle cost.
- D-033 separates normal correctness CI from browser/live verification.
- D-034 defines the performance evidence and headroom gate.
