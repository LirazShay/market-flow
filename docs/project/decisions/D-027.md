# D-027 — Browser SQL uses snapshot-centric wide core-horizon schema

Status: Accepted

## Decision

Local History Viewer V2 Browser SQL will use a snapshot-centric relational model with:

~~~text
security catalog
+ current universe membership
+ cycle records
+ one authoritative snapshot row per security per successful cycle
+ full raw Security JSON on the snapshot
+ a small typed/promoted analytical column set
+ wide nullable columns for the current eight core horizons
+ a latest_snapshot pointer table
~~~

Core horizon columns on snapshot include, per horizon:

~~~text
prev_H_snapshot_id
last_change_H_pct
deals_delta_H
~~~

for:

~~~text
10s, 20s, 30s, 60s, 90s, 120s, 300s, 600s
~~~

latest_snapshot stores only the security-to-snapshot pointer and does not duplicate the full snapshot row.

## Identity decisions

~~~text
security_id = VARCHAR / String(PaperId or Key)
snapshot_id = stable BIGINT surrogate
cycle_id    = stable BIGINT surrogate
session_id  = stable BIGINT surrogate
~~~

Snapshot natural uniqueness:

~~~text
UNIQUE(cycle_id, security_id)
~~~

Time does not define row identity.

## Raw + typed strategy

Full provider Security payload is retained as JSON.

Repeated high-value fields may also be promoted to typed columns.

The raw payload remains the preservation layer and the way to distinguish source key absence from explicit null when that distinction matters.

Typed columns are performance/query conveniences, not replacements for raw evidence.

## Why wide horizons

The current horizon set is small and heavily reused.

Wide columns avoid an additional horizon child-row set for every snapshot and keep common user SQL simple.

Flexibility remains through:

- one canonical horizon definition;
- explicit schema evolution when the core horizon set changes;
- arbitrary access to full linked historical snapshots;
- raw provider JSON;
- dynamic SQL for uncommon comparisons.

## Deals-delta boundary

Deals-delta columns may exist in the schema, but they must remain NULL/unpopulated until the provider cumulative-deal field semantics are Verified.

No semantic inference is authorized by this decision.

## Null/missing boundary

Promoted SQL NULL alone does not distinguish source-missing from explicit source-null.

Raw JSON preserves key presence and source value.

Queries that care about source presence must inspect raw JSON semantics.

## Deferred

This decision does not fix:

- bulk-ingest mechanism;
- transaction sequence;
- temporal-link selection algorithm;
- scheduler policy;
- retention;
- query metadata tables;
- OPFS checkpoint cadence;
- migration from IndexedDB.

Those remain later planning phases.
