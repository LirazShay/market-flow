# D-035 — Browser SQL cutover starts a fresh authority epoch without importing legacy IndexedDB history

Status: Accepted

## Decision

Initial Browser SQL cutover will not import existing Local History Viewer V2 IndexedDB history.

The transition is:

~~~text
IndexedDB authoritative
→ optional isolated SQL shadow verification
→ explicit stop boundary
→ fresh production OPFS authority
→ DuckDB/OPFS is the only active market-history authority
~~~

The legacy IndexedDB database remains physically untouched and inactive until an explicit later cleanup decision.

## Rationale

No current product requirement requires pre-cutover prototype history inside the SQL query surface.

A correct historical importer would add substantial complexity: ID remapping, idempotency, chronological horizon recomputation, latest/current reconstruction, interruption recovery and large-data verification.

KISS therefore favors a new SQL history epoch.

## Temporary coexistence

Pre-cutover SQL shadow/probe databases must have non-production identities.

IndexedDB remains the sole production authority during shadow verification.

Shadow failure cannot alter IndexedDB success semantics or production Viewer state.

Candidate data is never silently promoted into the production OPFS database.

## Cutover

Cutover occurs between settled cycles:

~~~text
stop IndexedDB Recorder
→ settle in-flight cycle
→ close legacy runtime ownership
→ start SQL cutover release
→ open/create verified production OPFS
→ SQL readiness
→ new SQL recording session
→ first durable SQL cycle
~~~

No cycle is intentionally split across authorities.

## No automatic fallback

After cutover, SQL startup/persistence failure does not silently switch writes or reads back to IndexedDB.

Recorder remains stopped/failed until explicit recovery or rollback.

The final runtime has no permanent dual-write, dual-read or automatic authority-selection layer.

## Historical coverage

SQL history begins at the first successful post-cutover SQL cycle.

Core horizon fields warm naturally and remain NULL until sufficient SQL history exists.

Legacy IndexedDB rows are not used as hidden predecessors.

## Rollback

Rollback is an explicit release switch:

~~~text
stop SQL runtime
→ preserve OPFS unchanged
→ launch retained IndexedDB runtime release
~~~

Because there is no post-cutover dual-write, rollback may have a documented history gap for the SQL-authority period.

SQL-period data remains preserved in OPFS for diagnosis and roll-forward; it is not automatically merged into IndexedDB.

## Cleanup

Legacy IndexedDB deletion is never automatic.

After a deliberate stabilization decision, migration/shadow scaffolding is removed and the user may explicitly delete the old local IndexedDB database.
