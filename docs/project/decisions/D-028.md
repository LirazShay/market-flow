# D-028 — Validated cycles commit atomically after SQL-side enrichment

Status: Accepted

## Decision

Local History Viewer V2 Browser SQL will persist each complete validated provider cycle as one logical bulk operation and one atomic SQL transaction inside the dedicated SQL Authority Worker.

Target flow:

~~~text
Recorder complete-cycle validation
→ immutable validated-cycle handoff
→ SQL Authority defensive validation
→ one bulk staging relation
→ set-based enrichment
→ one transaction
→ COMMIT
→ success acknowledgement
~~~

No cycle becomes successful market state before COMMIT.

## Handoff boundary

The Recorder owns provider collection and completeness validation.

The SQL Authority owns SnapshotId allocation, historical lookup, persisted enrichment, authoritative writes and successful-persistence acknowledgement.

The handoff includes the exact validated universe used for the cycle plus full raw MapHeat and GetSecuritiesData Security records and timing/integrity metadata.

## Bulk boundary

The application contract is one bulk operation per complete cycle, not one database round trip per security.

Arrow is the preferred internal bulk mechanism because current official DuckDB-Wasm capability research verifies first-class Arrow ingestion. Exact internal encoding remains benchmarkable without changing this contract.

## Enrichment split

Worker-side normalization may promote verified source fields into typed staging values while preserving full raw records.

Relational/historical enrichment is performed set-wise inside the SQL transaction so historical facts do not need to be copied back to JavaScript.

## Temporal predecessor rule

For horizon H, the persisted predecessor is the latest same-security snapshot with:

~~~text
previous.collected_at_ms <= current.collected_at_ms - H*1000
~~~

This provides deterministic jitter handling without exact timestamp equality or a generalized tolerance framework.

If no eligible row exists, the predecessor and dependent metrics are NULL.

## Atomic contents

The successful-cycle transaction coherently changes:

- complete cycle metadata;
- security/current-universe state for the exact cycle universe;
- one snapshot per security;
- temporal links;
- persisted derived metrics included in the snapshot contract;
- latest_snapshot pointers;
- recording-session successful-cycle metadata.

Any failure before COMMIT rolls the attempted cycle back.

## Query visibility

Scheduled/user analytical SQL may observe only committed market state.

The single SQL Authority coordination boundary prevents uncontrolled query/write interleaving. A query sees the previous committed cycle or the new committed cycle, never a partial mixture.

## current/latest rule

current_universe and latest_snapshot advance together with the successful cycle.

A security removed from the committed universe leaves current/latest but its historical snapshots remain stored.

## DealsDelta boundary

Current project evidence identifies DailyDealsQuantity as today's deal count and verifies availability in the measured snapshot, but reset/day-boundary semantics remain insufficiently verified for unrestricted historical subtraction.

Therefore persisted DealsDelta remains disabled/NULL until the reset contract is explicitly verified.

## Rebuildability

Persisted temporal links and derived metrics are optimizations, not source facts.

Raw/promoted values plus historical snapshots and timestamps must permit future SQL backfill/rebuild.

## Relationship to previous decisions

- D-025 fixes Browser-only SQL.
- D-026 fixes one dedicated SQL Authority Worker.
- D-027 fixes the snapshot-centric relational schema.
- D-028 fixes the ingest/enrichment/atomicity boundary.

## Deferred

This decision does not define query cadence/overrun/cancellation, persistence CHECKPOINT/reopen policy, runtime packaging, viewer transport or migration from IndexedDB.
