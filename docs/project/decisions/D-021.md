# D-021 — KISS: simplest sufficient design, complexity only when proven necessary

Status: Accepted

Decision:

Market Flow defaults to the **simplest coherent design that fully satisfies the current verified requirement and repository invariants**.

Use:

~~~text
current requirement + proven constraints
→ smallest sufficient mechanism
→ verify
→ stop
~~~

Do not introduce additional architecture, abstraction, generalized lifecycle, framework, loader/updater, cache, concurrency, retry orchestration, compatibility layer, or future-facing extension point merely because it may become useful later.

Additional complexity is justified when there is concrete present-day evidence such as:

- the current contract cannot be met cleanly without it;
- an observed bug/failure requires it;
- correctness, data integrity, security, testability, atomicity, or current recovery requirements require it;
- measured performance/reliability evidence requires it;
- a repeated concept has become stable enough that duplication creates real maintenance cost.

The following are not sufficient reasons on their own:

~~~text
"we may need it later"
"it is more flexible"
"it is more enterprise"
"let's make it generic now"
~~~

When choosing a more complex design, the work should be able to state why the simpler alternative is insufficient **now**.

KISS does not mean weakening validation, tests, observability, security, integrity, or required recovery guarantees. It means satisfying those guarantees with the minimum necessary machinery.

Why:

- every moving part adds implementation, testing, failure, debugging, and maintenance cost;
- speculative flexibility frequently solves problems that never materialize;
- simple verified designs are easier to understand, diagnose, replace, and evolve;
- architecture should grow from proven requirements rather than anticipated possibilities.
