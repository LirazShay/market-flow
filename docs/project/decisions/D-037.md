# D-037 — Browser SQL implementation follows gate-ordered executable work packages

Status: Accepted

## Decision

Browser SQL implementation will follow the Phase-P decomposition in:

~~~text
scripts/research/market-data/leumi/prototypes/local-history-viewer-v2/docs/browser-sql-implementation-decomposition.md
~~~

The plan contains:

~~~text
8 implementation milestones
41 executable work packages
6 hard gates
~~~

Each work package is intended to become one executable GitHub Issue in Phase Q.

## Gate-first rule

The real authenticated-Leumi compatibility probe is a hard implementation-entry gate.

Only the minimal engine pin/probe/test-harness work may precede it.

Heavy SQL-authority implementation must not proceed until the probe directly verifies:

~~~text
injected JS / Bookmarklet
→ Blob Worker
→ exact pinned DuckDB Worker/Wasm
→ OPFS write
→ COMMIT + CHECKPOINT
→ refresh/reopen
~~~

on the actual authenticated Leumi page using synthetic data only.

## Package contract

Every package owns:

- dependencies/blockers;
- explicit scope/non-goals;
- public acceptance criteria;
- cheapest valid test layer;
- verification/exit gate;
- SPEC/docs impact;
- temporary-artifact cleanup responsibility.

Packages should not be merged across hard gates merely to reduce Issue count.

## Temporary architecture rule

Probe/shadow/migration mechanisms are temporary and have explicit removal work.

The final production runtime must not retain permanent dual IndexedDB/DuckDB authority selection or shadow comparison paths.

## Execution management

Phase Q must materialize this decomposition into real GitHub execution management:

- milestones where useful;
- labels;
- 39 executable Issues;
- blocker/dependency references;
- parent/epic/checklist structure where supported by the available GitHub API.

Markdown decomposition alone is not the final project-management deliverable.
