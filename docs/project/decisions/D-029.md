# D-029 — Analytical SQL uses immutable versions and a non-overlapping anchored scheduler

Status: Accepted

## Decision

Local History Viewer V2 will treat user analytical SQL as a first-class immutable versioned artifact executed by a deterministic scheduler inside the dedicated SQL Authority Worker.

The baseline contract is:

~~~text
immutable query version
→ read-only analytical safety gate
→ fixed wall-clock cadence anchored to activation
→ at most one query execution
→ missed ticks coalesce
→ validated cycle commit has priority over pending analytical work
→ query only committed market state
→ latest execution and latest successful execution remain distinct
~~~

## Query identity

Changed SQL creates a new immutable query version.

Every execution records the exact query_version_id that produced its result/error.

An already-running execution keeps the version captured when it started. Activating a new version affects only later executions.

## Read-only analytical boundary

User analytical SQL is separate from trusted Market Flow schema/admin SQL.

The analytical contract accepts one result-producing query statement and rejects DDL, DML, transaction control, extension/configuration commands and other administrative statements.

Safety classification must be parser/statement-type based. Prefix/regex-only detection is not sufficient.

Because the same database instance must remain writable for ingest, database-level READ_ONLY access mode cannot by itself implement the analytical safety boundary.

## DuckDB hardening direction

Where verified in the pinned DuckDB-Wasm build, runtime setup should disable external access and uncontrolled extension/configuration paths before enabling user analytical SQL.

Relevant official DuckDB controls include:

~~~text
enable_external_access = false
autoinstall_known_extensions = false
autoload_known_extensions = false
allow_community_extensions = false
lock_configuration = true
~~~

Required trusted extensions/capabilities must be established before the configuration is locked.

## Scheduler clock

The scheduler uses fixed cadence anchored to activation:

~~~text
due(n) = schedule_anchor_ms + n * interval_ms
~~~

It does not schedule "interval after previous completion", which would drift.

Collection cadence and analytical cadence are independent.

## No overlap and coalescing

At most one analytical execution runs.

If one or more scheduler ticks become due while the database authority is busy, they produce at most one pending analytical execution opportunity.

After the authority is available, missed ticks do not burst-execute.

The next due boundary advances to the first future anchored cadence point.

## DB-operation priority

After the currently running operation finishes:

~~~text
1. validated successful-cycle commit
2. one pending analytical execution
3. maintenance allowed by later contracts
~~~

This prevents analytical backlog from outranking fresh market-data persistence.

## Query consistency

Queries run only against coherent committed market state.

They never intentionally interleave with a successful-cycle transaction in the baseline single-authority design.

## Result/failure state

Zero rows is a successful result.

The runtime keeps distinct identities for:

~~~text
latest_execution
latest_successful_execution
~~~

A failed execution never silently replaces the previous successful result.

## Result materialization

The planned query path streams Arrow batches and counts the complete result while only materializing a bounded Viewer payload.

The SQL text is not silently rewritten with LIMIT.

The exact Viewer preview cap remains a later UX/benchmark decision.

## Cancellation boundary

Current research has not verified a public hard-interrupt API for the selected DuckDB-Wasm surface.

Therefore hard cancellation is not part of the baseline contract.

Until a pinned package proves safe interruption:

- long-running queries are observable;
- query executions do not overlap;
- the authority Worker is not terminated merely to fake timeout semantics;
- performance gates must keep intended live queries comfortably within cadence.
