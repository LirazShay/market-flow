# D-044 — Browser SQL V2 uses a post-KISS minimum SQL core, product-first migration and evidence-triggered optimization

Status: Superseded by D-045 for Local History Viewer V2

## Current clarification

The post-KISS Browser-SQL implementation baseline is frozen and is no longer executable.

Its product-first/KISS principles remain useful, but the Worker/Wasm/OPFS/Web-Lock runtime topology and C01-C12 execution graph are superseded by the Node.js localhost re-plan owned by D-045 and current STATUS.

The historical baseline below is retained for traceability.

## Decision

Local History Viewer V2 will implement Browser SQL with the smallest architecture that satisfies the current verified product and integrity requirements.

The current implementation baseline is:

~~~text
existing authenticated V1 provider flow
→ one Runtime Controller / SQL Authority Worker
→ pinned DuckDB-Wasm + persistent OPFS
→ atomic raw/current/history SQL authority
→ small trusted read API
→ Current Universe + Security Detail/History
→ simple read-only Dynamic SQL Scanner
→ one exclusive Web Lock owner
→ representative daily workload
→ explicit cutover
~~~

D-043 remains the product/data boundary. This decision owns the post-KISS implementation baseline.

## Minimum SQL core first

Initial SQL authority stores only the raw/current/history state required for the V1-on-SQL product and future SQL access.

No fixed analytical horizon schema, predecessor-link matrix or persisted metric set is mandatory before real queries demonstrate a need.

Full raw MapHeat and Security facts remain preserved.

## Complete-cycle atomicity

A complete validated provider cycle remains the unit of successful persistence.

The SQL authority must expose either the previous committed cycle or the new complete committed cycle, never a partial mixture.

The exact production durability/checkpoint/retry mechanism is evidence-driven. A fixed COMMIT→CHECKPOINT→ack ritual or ingest-token subsystem is required only if the selected DuckDB-Wasm/OPFS behavior and acknowledgement boundary prove it necessary.

## Evidence-triggered analytical optimization

Start with real SQL over raw/history data.

~~~text
real analytical query
→ representative day-sized measurement
→ if sufficient: stop
→ if insufficient: add the smallest targeted optimization
~~~

Persisted horizons, typed promotions, predecessor references, derived metrics or indexes are implementation choices only after verified semantics and measured value justify them.

Unknown provider semantics are never guessed.

## Simple Scanner

The initial Dynamic SQL Scanner uses:

~~~text
draft SQL + interval
→ explicit Activate
→ one active SQL/config
→ read-only execution
→ at most one execution at a time
→ no burst replay
→ truthful result/error rendering
~~~

Immutable query-version history, optimistic multi-editor concurrency, anchored scheduler machinery, mandatory streaming and advanced cancellation/preemption are not initial requirements.

If mixed-load evidence shows a real problem, add only the smallest mechanism required.

## Viewer and ownership

Viewer remains a client of the Runtime Controller/SQL Authority and never becomes an independent DuckDB/OPFS owner.

Notifications are hints; authoritative state is reread.

Cross-tab production ownership uses one stable exclusive Web Lock. Chromium proves the mechanism during implementation; authenticated-origin two-tab proof is required before final cutover, not as an early blocker for all SQL work.

## Storage and lifecycle

Initial production policy is:

~~~text
retain committed history
→ no silent pruning
→ no silent reset
→ explicit failure when safe persistence cannot continue
~~~

Archive/rollover, generalized schema/engine upgrade machinery and restore/import are conditional or future work, not standing initial-V2 subsystems.

Unsupported DB/schema compatibility blocks writable startup and preserves the DB unchanged.

## Performance and verification

Performance is judged by representative product behavior, not fixed abstract ratios.

The shipped candidate must prove a representative daily mixed workload without unbounded persistence backlog, Scanner overlap, data-integrity failure, crash/OOM or storage failure for the required workload.

Verification follows:

~~~text
Node
→ pure deterministic logic

Chromium
→ Worker/Wasm/OPFS/runtime/Viewer/Web Locks/Scanner integration

authenticated Leumi
→ real origin/provider facts that CI cannot prove
~~~

Normal permanent workflows remain Fast CI and Browser CI.

## Cutover

Initial cutover remains deliberately simple:

~~~text
stop old IndexedDB Recorder at a settled boundary
→ preserve legacy IndexedDB data
→ start fresh SQL production history
→ DuckDB/OPFS becomes the only new market-history authority
~~~

No legacy history import, permanent dual authority or automatic fallback is required.

Rollback is an explicit release switch back to the retained old release while preserving the SQL DB for diagnosis.

## Execution graph

The compact implementation graph is one Master plus C01..C12 executable Issues.

No checkpoint-only Issues and no standing conditional/future Issues are required.

Conditional work is created only from evidence triggers, including:
- targeted analytical optimization;
- advanced Scanner resource hardening;
- streaming/chunked result delivery;
- storage/export/fresh-DB workflow;
- target-environment performance evidence;
- temporary shadow comparison.

Canonical dependency rationale:

~~~text
scripts/research/market-data/leumi/prototypes/local-history-viewer-v2/docs/browser-sql-compact-execution-dag.md
~~~

Current live progress remains only in STATUS.json.
