# D-036 — Browser SQL uses scoped failures, worst-active health precedence and sanitized local observability

Status: Accepted

## Decision

Local History Viewer V2 Browser SQL failures are scoped to the smallest affected subsystem.

Operational health is separate from runtime lifecycle and uses:

~~~text
healthy
degraded
blocked
recovery-required
~~~

Overall health is the worst active component state:

~~~text
recovery-required > blocked > degraded > healthy
~~~

An unrelated later success cannot clear a more severe active failure from another component.

## Retry boundary

There is no generic automatic retry engine.

Examples:

- transient provider/validation failure → next normal collection cycle;
- active query execution failure → next scheduled query tick;
- Viewer disconnect → reattach/resync;
- unexpected SQL Worker loss → one controlled reopen/recovery attempt;
- quota/CSP/schema/corruption/durability uncertainty → no blind retry; block or require recovery.

Retries are allowed only where idempotency and authority semantics are defined.

## Failure isolation

Expected command-local SQL activation errors do not degrade a healthy runtime.

Active query execution errors degrade the analytical subsystem but do not stop ingest.

Viewer failures do not change core runtime health.

Persistence/durability/schema failures can block recording or require explicit recovery.

## Security

Provider authentication remains in the authenticated Leumi page.

SQL Worker, Viewer, generated artifacts and diagnostics must not receive or persist cookies, authorization headers, session tokens, account numbers or private session-storage data.

User SQL is local data; downloadable diagnostics omit full SQL text and arbitrary query-result rows by default.

Analytical SQL remains constrained by the read-only classification and DuckDB hardening defined by D-029.

## Observability

Purpose-specific durable records remain the evidence owners:

~~~text
recording_session
cycle
query_version
query_execution
~~~

Do not add an unbounded generic event database by default.

Runtime may keep bounded recent sanitized incidents for Viewer/debugging, including failures that happen before the DB can open.

The existing sanitized Debug Bundle concept is retained and extended for Browser SQL.

## Telemetry

There is no external telemetry service in the baseline Browser SQL target.

Any future remote telemetry requires a separate explicit security/privacy decision.
