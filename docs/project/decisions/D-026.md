# D-026 — Browser SQL uses one dedicated SQL Authority Worker

Status: Accepted

## Decision

Local History Viewer V2 Browser SQL will use one dedicated SQL Authority Worker as the sole runtime owner of the authoritative persistent DuckDB-Wasm/OPFS database.

Target boundary:

~~~text
authenticated Leumi page
→ Recorder
→ Runtime Controller
→ dedicated SQL Authority Worker
   → DuckDB-Wasm
   → persistent OPFS database
   → successful-cycle commits
   → active SQL scheduler
   → query execution

Viewer(s)
→ read-only clients through the runtime bridge
→ no direct authoritative DB handle
~~~

The baseline is the normal single-threaded DuckDB-Wasm path.

The `coi` threaded bundle is optional future optimization only and is not required for correctness or the target architecture.

## Rationale

Phase D evidence established:

- DuckDB-Wasm's normal async model is Worker-based;
- OPFS persistence is a documented capability;
- OPFS synchronous access belongs in Workers;
- OPFS handle ownership is constrained;
- cross-tab/multi-instance OPFS access is not sufficiently proven for Market Flow;
- single-thread operation is the normal supported baseline;
- Leumi cross-origin isolation is Unknown.

One SQL authority therefore minimizes unproven concurrency, duplicate ownership and recovery complexity.

## Consequences

- Recorder remains responsible for authenticated provider collection and complete-cycle validation.
- Recorder does not write DuckDB directly.
- SQL Authority Worker coordinates all authoritative DB writes and analytical SQL execution.
- Successful-cycle exposure remains commit-after-validation.
- Viewer windows do not open their own authoritative DuckDB/OPFS handles.
- SQL scheduler logically belongs to the SQL Authority Worker.
- Runtime Controller orchestrates lifecycle and message bridging but is not market-history authority.
- Persistent SQL DB becomes the target market-history source of truth after migration cutover.
- IndexedDB can exist only as transitional migration state, not permanent co-authority.
- Connection count, internal queue policy and detailed scheduling remain later design details.

## Recovery consequence

The Worker itself is ephemeral.

Committed market history must be recoverable by creating a new SQL Authority Worker and reopening the persistent database after page/runtime restart.

Exact checkpoint/reopen policy is owned by the persistence/recovery planning phase.

## Security consequence

Provider cookies/session tokens/authorization remain in the authenticated page.

The SQL Authority receives validated market data and analytical commands; it does not require copied authentication secrets.

## Relationship to earlier decisions

- D-025 fixes Browser-only SQL as the process boundary.
- D-026 fixes the single-authority Worker topology inside that boundary.
- D-021 KISS supports avoiding SharedWorker/multi-handle/multi-owner complexity without evidence.
- D-001 requires later benchmark/browser evidence for performance and runtime claims.

## Evidence level

Architecture choice: **Accepted**.

DuckDB-Wasm/OPFS capability: **Verified at documentation level**.

Exact package-version durability, Leumi CSP compatibility, Market Flow-scale performance and long-run stability: **still require later verification**.
